# ADR-0002: Модель данных — три признака на каждый срез + дата первого появления

Дата: 05.11.2026
Статус: принята (подтверждена проверкой H-02)

## Контекст

Заказчик согласовал 7 состояний клиента: все переданы, впервые, уменьшается,
не меняется или растёт, повторное, хронический, новичок. Состояния сочетаются
(например, «хронический» и «уменьшается» одновременно), историю срезов хранить
требует ТЗ. Сравнивались два способа хранения: А) одно поле «категория»
у клиента; Б) три отдельных признака на каждый срез + дата первого появления.

## Решение

Храним по каждому клиенту в каждом срезе три отдельных признака
(модель Б, решение Р-02):

1. `dynamics_code` — изменение между срезами: NO_COMPARISON, ALL_TRANSFERRED,
   FIRST_APPEARED, DECREASING, FLAT_OR_GROWING, REAPPEARED;
2. `is_novice` — «новичок» (признак клиента: подключён менее 6 месяцев назад);
3. `is_chronic` — «хронический» (ситуация сохраняется: непереданные > 0, этап
   дальше «Выявлены», в предыдущем квартале непереданные были, обнулений не было).

Плюс `client.first_appearance_date` — дата первого появления клиента.
Срезы не перезаписываются (SN-01). Итоговая категория для показа выводится
приоритетом: Нет сравнения → Нет данных → Хронический → Новичок (при not>0) →
изменение. Поле категории в БД не хранится — выводится из трёх признаков.

## Обоснование (H-02, 05.11.2026)

- 18 из 18 допустимых сочетаний записываются без противоречий; модель А
  сворачивает 10 из 18 с потерей информации.
- Восстановление состояния на прошлые срезы только по сохранённым данным:
  модель Б 211/211, модель А 0.
- Совпадение с ручным расчётом: 86/86 (контрольная книга DS-02) и 187/187
  строк, 51/51 клиентов (ручная разметка 50 клиентов) — критерий «≥ 49 из 50»
  выполнен; единственное расхождение (флаг «новичок» при not=0) — конвенция
  отображения, зафиксирована в карточке H-02.
- Время пересчёта 0,02 с на срез 3 000 строк (требование H-04 — до 60 с).

## Последствия

- В `document_snapshot` три поля признаков (см. `backend/models.py`).
- Правила расчёта **перенесены** в `backend/dynamics/features.py` и вызываются после успешного импорта; проверки описаны в `backend/tests/test_h02_dynamics.py`.
- Повторная загрузка той же даты среза **в текущем MVP отклоняется** ответом `409` (SN-04); возможность версионирования требует отдельного решения заказчика.

## Уточнение правила «новичок» (17.11.2026)

Выбран первый вариант: `is_novice` — независимый признак клиента на дату среза (подключён менее шести календарных месяцев назад), **даже если непереданных документов ноль**. В интерфейсе метка «Новичок» показывается только при `missing_documents > 0`; API отдаёт раздельно `is_novice` и `show_novice_badge`. Это устраняет расхождение в представлении 6 строк разметки и не теряет информацию о клиенте.

После успешного импорта нового среза выполняется пересчёт модели Б по истории затронутых клиентов. Не удаляются и не перезаписываются исторические исходные строки срезов (SN-01); меняются только вычисляемые поля признаков, которые пересчитываются из сохранённой истории. Повторная дата среза для одного клиента и периода отклоняется кодом 409 (SN-04); версия загрузки требует отдельного согласования.

Реализация: `backend/dynamics/features.py` — перенос исходных правил, `backend/dynamics/service.py` — сохранение вычисляемых полей, `GET /api/clients/{client_id}/dynamics` — история.

## Сверка документа с backend (17.11.2026)

- В `backend/dynamics/service.py` сохраняются `is_novice` и `is_chronic` в `document_snapshot`; `show_novice_badge` вычисляется в `present()` и возвращается в API. При нуле непереданных флаг может быть `true`, а метка — `false`.
- Исходные `total_documents`, `missing_documents`, `snapshot_date`, `reporting_period` не заменяются при пересчёте, однако **расчётные поля старых срезов могут пересчитываться**.
- Ограничение: `is_chronic` для исторических записей использует текущий активный этап работы, т. к. история этапов пока не реализована.
- Для повторного среза того же квартала пустое `total_documents` разрешено, если опорный срез клиента этого периода уже сохранён.
